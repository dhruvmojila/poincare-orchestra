    API reference¶

    Everything below is importable from poincare_orchestra unless noted. Public API changes are additive and listed in the changelog.

    Scenario model¶

    scenario ¶

    Scenario model: a use case is data, not code.

    A scenario bundles the domain hierarchy and dated facts that seed the memory, the specialist roles and their capability profiles, example tasks with the facets a good answer must cover, and the controller policy. Everything the orchestrator does is driven by it, so a new use case is a new scenario file (JSON or YAML; see :meth:Scenario.from_file).

    OBJECTIVES module-attribute ¶

    OBJECTIVES: tuple[str, ...] = ('coverage', 'density', 'agreement', 'recency', 'cost')

    The five synthesis objectives a policy may weight or constrain.

    DECAY_KINDS module-attribute ¶

    DECAY_KINDS: tuple[str, ...] = ('none', 'half_life', 'ebbinghaus', 'validity')

    Accepted kinds in a ControllerPolicy.decay spec.

    Scenario ¶

    Bases: BaseModel

    A complete use case: memory contents, roles, capability profiles, tasks and policy.

    Validation runs on construction and on :meth:from_file: duplicate ids, parents declared after their children, roles that reference unknown profiles and tasks without facets are reported with their position.

    build_memory ¶

    build_memory(now: datetime | None = None, clock: Callable[[], datetime] | None = None, **kwargs: Any) -> Memory

    Seed a fresh :class:poincare_memory.Memory with the knowledge items.

    now anchors the relative dates (default: the current UTC time); clock overrides the memory's clock; other keyword arguments go to Memory (for example embedder=).

    to_file ¶

    to_file(path: str | Path, format: FileFormat | None = None) -> Path

    Write the scenario as JSON or YAML; the format follows the suffix unless given.

    YAML needs PyYAML (pip install 'poincare-orchestra[yaml]').

    from_file classmethod ¶

    from_file(path: str | Path, format: FileFormat | None = None) -> Scenario

    Load and validate a scenario from a JSON or YAML file.

    Raises:

    Type Description
    FileNotFoundError

    if path does not exist.
    ValueError

    if the suffix is not .json/.yaml/.yml and no format is given, or if the file is not a mapping.
    ValidationError

    if the contents are inconsistent (see the class docstring).
    ImportError

    for YAML without PyYAML installed.

    parent builds the hierarchy (parents must be listed before their children); days_ago dates a record relative to the run; the two valid_* fields give it a validity window for the validity decay kind.

    Bases: BaseModel

    Budget, retrieval, objective weights, epsilon constraints and temporal policy of a scenario.

    max_subtasks: int = Field(default=4, ge=1)

    total_budget class-attribute instance-attribute ¶

    total_budget: float = Field(default=6.0, gt=0)

    min_budget class-attribute instance-attribute ¶

    min_budget: float = Field(default=0.5, ge=0)

    retrieval_k class-attribute instance-attribute ¶

    retrieval_k: int = Field(default=5, ge=1)

    objectives class-attribute instance-attribute ¶

    Weights w_i of eq. 7; keys must be objective names.

    constraints class-attribute instance-attribute ¶

    constraints: dict[str, float] = Field(default_factory=lambda: {'coverage': 0.5, 'density': 0.2})

    refine_rounds class-attribute instance-attribute ¶

    refine_rounds: int = Field(default=1, ge=0)

    decay class-attribute instance-attribute ¶

    decay: str = 'half_life:720'

    none | half_life:<hours> | ebbinghaus:<hours> | validity | half_life:<h>+validity

    parse_decay ¶

    parse_decay(spec: str) -> DecayPolicy

    Build a poincare_memory decay policy from a spec string.

    Grammar: none | half_life:<hours> | ebbinghaus:<hours> | validity, and any of these joined with + for a product (for example half_life:2160+validity). Hours default to 720 (half-life) and 168 (Ebbinghaus stability) when omitted.

    Raises:

    Type Description
    ValueError

    if a kind is unknown or an hour value is not a positive number.

    load_scenario(name: str | Path) -> Scenario

    Raises:

    Type Description
    KeyError

    if name is neither a bundled scenario nor an existing file.
    FileNotFoundError

    if name looks like a scenario file but does not exist.

    Controller¶

    controller ¶

    Metacognitive controller (paper §III-B, §III-C, §IV-B).

    Four executive functions, each a small, inspectable step: 1. query analysis and intent recognition, with the memory hierarchy as the domain model; 2. hierarchical decomposition into coordinated sub-tasks Q -> {q_1..q_n} (eq. 5); 3. capability matching of sub-tasks to roles and profiles; 4. resource allocation by expected information gain per cost, I*(q_i) = argmax_I G(q_i, I) / C(I) (eq. 6), run as an investment cycle: invest, measure yield, re-invest the remainder.

    The implementation is rule-based and offline so the control loop is transparent; an LLM-backed planner can replace decompose without touching the rest.

    ThrottleDetector ¶

    ThrottleDetector(window: int = 6, min_history: int = 2, latency_factor: float = 3.0, length_ratio: float = 0.4, density_drop: float = 0.35)

    Flags responses whose latency, length, density or refusal pattern breaks the provider's baseline.

    The baseline is the provider's own recent responses (the last window that were not flagged); while a provider has fewer than min_history of them, the pooled responses of all providers stand in for it. A response is flagged when it is refused, when its latency exceeds latency_factor times the baseline median, when its token count is below length_ratio times the baseline median, or when its information density is more than density_drop below the baseline median. Flagged responses do not enter the baseline.

    Router ¶

    Router(providers: list[Provider], profiles: list[CapabilityProfile], detector: ThrottleDetector | None = None, cooldown_calls: int = 3)

    Chooses a provider for each role by capability profile and health; fails over on throttling.

    Candidates are ordered by: the profile's preferred provider first, then providers that are not cooling down, then the least loaded. A flagged response or a provider exception puts the provider in cooldown: it is skipped for the next cooldown_calls calls and the next candidate is tried; the last response is returned if every candidate fails. When every provider is cooling down they are tried anyway, least-degraded first, so a call never fails only because of cooldowns. call never raises on a provider exception: it is converted into a refused :class:AgentResponse and a :class:ThrottleEvent with reason error: <exception type>.
